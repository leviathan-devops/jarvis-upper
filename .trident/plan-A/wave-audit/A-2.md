## §4 THE FALSE-GREEN GUARD — the load-bearing property, PROVEN BY MY OWN PROBE

I ran an adversarial probe with a `fetchImpl` that throws:

```ts
const boom = async () => { throw new Error("rail down"); };
const r = await publishStatus({...fetchImpl: boom}, {context:"factory/fence2", state:"success", ...});
```

The observed result, verbatim:
```
throwing fetch -> {"context":"factory/fence2","state":"error","status":null,"ok":false,
                   "reason":"FETCH-THREW:rail down"}
VERDICT: CORRECT (never false-green)
```

**This is the property the whole design exists for.** A publish that cannot confirm does NOT
claim green. The `catch` at `src/publish.ts:59` routes to `state: "error"` at line 62 — and a
non-2xx response routes to `HTTP-${res.status}` at line 74. Both are loud failures, neither is
a silent success.

## §9 THE HONEST REMAINDER

- **No real POST has been made.** Every test and probe uses an injected `fetchImpl`. The live
  path (a real GitHub status POST) is untested until the T2/A-4 integration with a scratch sha.
- **`publishVerdict` posts sequentially, not in parallel.** The desk noted the seam: a shared
  description truncates identically on both posts. Not a defect, but A-4 must decide whether the
  two statuses carry distinct descriptions.
- **No retry on a non-2xx.** That is deliberate (the desk's note: *"a single refused write is the
  verdict, never retried into silence"*) and correct per the loud-fail law — but it means a
  transient 5xx burns a publish. If the operator wants retry-with-backoff, that is a new decision.
- **The token default reads `GH_TOKEN` then `GITHUB_TOKEN`.** Neither is set in this session; the
  live publish will need one. Not a code defect; an environment prerequisite.
