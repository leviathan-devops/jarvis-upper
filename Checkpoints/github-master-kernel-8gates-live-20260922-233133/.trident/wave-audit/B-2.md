## §3 ★ THE AUDIT-METHOD DEFECT I MADE (and the lesson)

**My first check reported a false defect.** I ran:

```bash
bun run scripts/spec-diff.ts | tail -12 ; echo "spec-diff exit: $?"
```

which printed `SPEC-DIFF:mapped=14 unmapped=6` and `exit: 0` — so I concluded the gate
reports unmapped items but cannot block. **That conclusion was WRONG.**

**The cause: the pipe.** `cmd | tail` returns **tail's** exit status, not the script's. The
script's real exit code, read without a pipe:

```bash
bun run scripts/spec-diff.ts > /tmp/sd.out 2>&1 ; echo "RAW exit code: $?"
-> RAW exit code: 1
```

`src/spec-diff.ts:74` is `process.exit(unmapped > 0 ? 1 : 0)` — **the gate blocks correctly.**

### THE LAW THIS EARNS

**An audit that pipes a gate's output reads the WRONG exit code.** The verification method is
part of the verification. A gate can be perfect and an audit can still report it broken — if
the audit's own pipeline eats the signal. This is the same class as a probe with no exit
condition: the instrument, not the subject, was at fault.

**The desk's claim was CORRECT.** I was the source of the false defect.

## §6 THE CI JOB GUARDS (the belt-and-braces)

Each job's run step carries its own `|| exit 1`:

```yaml
  "gates/spec-gate":
    steps:
      - name: every spec item maps to a changed file
        run: bun run scripts/spec-diff.ts || exit 1
      - name: the fence must hold a PASS row for this sha
        run: python3 gates/fence-check.py "${{ github.sha }}" || exit 1
```

The `|| exit 1` is redundant with the script's own exit code — but it is correct defence: if a
script were ever changed to exit 0 on a soft failure, the job still blocks. **Not a defect.**
