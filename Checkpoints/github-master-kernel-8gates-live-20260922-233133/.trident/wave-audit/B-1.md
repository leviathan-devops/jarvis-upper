## §2 WHY — does the reason hold against the spec?

The wave's spec (`Parallel_Build_Spec_v1.md` §B-1) required:
1. `core.hooksPath .githooks` — the L5 fix, because `.git/hooks` is never versioned.
2. `prepare-commit-msg` carrying W-8 — the absolute anchor (L4).
3. `pre-commit` carrying W-1, W-6, W-9.
4. `pre-push` refusing `refs/heads/main`.

**Every requirement is met.** The hook's own header quotes the git manual verbatim on the
`--no-verify` asymmetry — *"prepare-commit-msg is not suppressed by the --no-verify option"* —
which is the correct design rationale, not an invented one. I verified that quote against
`https://git-scm.com/docs/githooks` earlier this session.

## §3 HOW — the blast radius

`core.hooksPath=.githooks` is a **repo-local git config**, not a tracked file. Consequences:

- It affects THIS clone only. A fresh clone must run `git config core.hooksPath .githooks` once.
- The hooks themselves ARE tracked (`.githooks/` is in the worktree) — so the content propagates,
  the config does not. This is the standard limitation; the re-host guide (`§14.2` step 2) names it.
- `pre-push` now refuses `refs/heads/main` — which means the orchestrator's own pushes to main
  from this repo are blocked by design. That is intended (B-1's exit criteria) and is the local
  half of the ruleset's protection.

## §7.9 THE FLAWED HUNK — W-1 ported without its layout (FOUND AND FIXED)

**The verdict on this hunk: FLAWED as delivered, CORRECT after the orchestrator's fix.**

### The defect

W-1's predicate was derived from a MEASURED GI-kernel instance:

```
extensions/graph-intelligence/index.js  Sep 20 07:11
src/omp/*.ts                            Sep 21 17:5x
-> every fix UNLOADED. 21-35 h stale.
```

That repo HAS an `extensions/` directory. `jarvis-upper` does NOT:

```
$ ls -d extensions/
ls: cannot access 'extensions/': No such file or directory
```

**Consequence:** the gate as written could NEVER pass in this repo — every `src/` commit was
refused forever. A gate that fires on everything is a gate that gets bypassed, which is worse
than no gate at all.

### The evidence it fired

The orchestrator's own commit attempt:

```
REJECT(W-1): staged src/ change with no staged extensions/ change
```

### The fix (applied by the orchestrator, recorded here)

`.githooks/pre-commit` — the condition gained a directory guard:

```bash
if [ -d extensions ] && [ "$SRC_TOUCHED" -eq 1 ] && [ "$EXT_TOUCHED" -eq 0 ]; then
```

plus a 7-line header comment explaining the scoping and why an unscoped port is a defect.

### The fix verified

| the test | the result |
|---|---|
| `bash .githooks/pre-commit` with `src/` staged, no `extensions/` | `PRE-COMMIT: PASS`, exit 0 |
| the negative control (a repo WITH `extensions/`) | the guard evaluates — the check is preserved where it applies |

### THE LAW THIS EARNS

**A gate is a (predicate × layout) pair.** Porting a predicate without verifying the target's
layout produces a gate that either fires on nothing or fires on everything. Both are failures.
This is the same class as the `store.ts` SQL CHECK — a second source of truth that drifts.
